# 트래픽 용량과 요금 (2026-11-22 저녁)

주인 질문: "트래픽이 많아지면 지금(무료) 얼마나 버티는지, Cloudflare 유료 5달러·Supabase 유료 25달러(월)로는 얼마나 버티는지, 예전 트래픽 최적화 로직이 맞는지."

숫자는 두 가지를 곱한 것이다. 하나는 플레이어 한 명이 한 시간에 쓰는 양(로컬 서버에서 두 탭과 봇 1·5·10·50명으로 잰 값과 코드에서 계산한 값), 다른 하나는 요금제 한도(공식 문서, 아래 출처)다. 실서비스 사용량을 몇 주 본 값이 아니므로 ±50% 정도로 읽는다.

"플레이어-시간"은 한 사람이 한 시간 놀았다는 단위다. 30명이 4시간 놀면 120 플레이어-시간이다.

## 한 줄 답

| | 하루에 버티는 양 | 예 |
| --- | --- | --- |
| **지금 (둘 다 무료)** | 약 **200 플레이어-시간** | 25명이 8시간, 또는 50명이 4시간 |
| **Cloudflare 유료 $5** | 사람 수로는 거의 무제한, 동시 접속은 **400명**(방 8개 × 50명, 코드 상수) | 하루 1,000 플레이어-시간(100명 × 10시간)이면 월 약 **$6**. 400명이 24시간 내내 꽉 차면 월 약 **$100~170** |
| **Supabase 유료 $25** | Cloudflare 유료와 같이 쓸 때 위 숫자를 그대로 받친다 | 무료로도 하루 500 플레이어-시간 안팎까지는 버티지만, DB 500MB가 몇 달 안에 찬다 |

무료에서 먼저 막히는 것은 사람 수가 아니라 **Cloudflare의 하루 한도**(UTC 0시 = 한국 오전 9시에 초기화)다. 넘으면 그날 오전 9시까지 실시간 방이나 저장이 실패한다. 게임에는 80%에서 줄이고 95%에서 막는 장치가 있다.

## 플레이어 한 명이 한 시간에 쓰는 양 (이번 수정 뒤)

| 항목 | 움직이며 노는 사람 | 가만히 서 있는 사람 | 숨긴 탭 (5분이 지난 뒤) |
| --- | --- | --- | --- |
| Worker 요청 | 약 90~150 (+ 접속할 때 16) | 12 | 0 |
| 실시간 방(DO) 요청 | 약 250 (움직임 메시지 ÷ 20 포함) | 방 공용 몫만 | 0 (5분까지는 가만히와 같음) |
| DO 저장소 줄 쓰기 | 약 350~600 (코인을 벌 때) | 적음 | 0 |
| Supabase 호출 | 약 90~150 | 거의 0 | 0 |
| 방이 깨어 있는 시간 | 방 하나가 한 시간 깨어 있으면 450 GB-s (사람 수와 상관없음) | | |

- 그림·모델 같은 정적 파일은 Worker를 실행하지 않아 요청 수에 들어가지 않는다(`wrangler.jsonc` `run_worker_first`는 `/rt/*`뿐).
- 서버가 보내는 메시지는 무료다. 그래도 방 하나에 50명이면 서버가 초당 약 2,000개를 보내고, 휴대폰 한 대가 받는 양은 초당 약 4KB(시간당 약 14MB)다.

## 무료에서 어느 한도에 먼저 닿나

| 한도 (하루) | 닿는 때 |
| --- | --- |
| DO 저장소 줄 쓰기 10만 | 코인을 버는 플레이어-시간 약 **200** ← 가장 먼저 |
| DO 요청 10만 | 약 300(80%, 줄이기 시작) ~ 365(95%, 막기) |
| Worker 요청 10만 | 약 800 |
| DO 실행 시간 13,000 GB-s | 방 하나는 24시간 깨어 있어도 10,800이라 괜찮다. 방 두 개가 오래 붐비면 넘는다 |

**주의**: 게임의 하루 예산 장치는 DO 요청과 실행 시간만 센다. **줄 쓰기와 Worker 요청은 세지 않는다.** 그래서 무료에서 사람이 몰리면 장치가 줄이기 전에 줄 쓰기 한도가 먼저 차서, 그날 남은 시간 동안 코인 적립 같은 저장이 실패할 수 있다. 출시 전에 고치거나 유료로 가는 것이 안전하다(아래 "남은 것").

## Cloudflare 유료($5)에서의 요금

포함량: Worker 요청 월 1,000만, DO 요청 월 100만, DO 실행 시간 월 40만 GB-s, 줄 쓰기 월 5,000만, 줄 읽기 월 250억.
넘으면: DO 요청 100만당 $0.15, 실행 시간 100만 GB-s당 $12.50, 줄 쓰기 100만당 $1.00, Worker 요청 100만당 $0.30.

| 경우 | 월 사용 | 월 요금 |
| --- | --- | --- |
| 하루 200 플레이어-시간 (지금 무료 한계) | 6,000 플레이어-시간 | $5 (포함량 안) + DO 요청 약 $0.08 |
| 하루 1,000 (100명 × 10시간, 방 2개) | 3만 | 약 **$6** |
| 하루 4,000 (평균 170명이 하루 종일, 방 4개) | 12만 | 약 **$25~45** (실행 시간 약 $11, 줄 쓰기 $0~22, DO 요청 약 $4) |
| 최대: 400명이 24시간 내내 (방 8개 꽉 참) | 28.8만 | 약 **$100~170** (줄 쓰기 $50~120, 실행 시간 약 $27, DO 요청 약 $11, Worker 약 $7) |

동시 접속 400명은 코드에 정해 둔 방 수(8개 × 50명) 때문이다. 늘리려면 방 수를 늘리면 되고, 요금은 사람 수에 비례해 늘어난다.

**유료로 바꿀 때 꼭 할 것**: `PLAN=paid`만 넣으면 예산 장치가 하루 DO 요청 3,000만 건, 300만 GB-s까지 허용한다. 그 끝까지 가면 한 달 최대 약 $1,200이 될 수 있다(실제 놀이로는 닿기 어렵지만 공격이면 가능). 그래서 같이 넣는다.

- Worker 변수 `BUDGET_REQ_DAY=5000000` (하루 DO 요청 500만, 넘어도 월 최대 약 $22)
- Worker 변수 `BUDGET_GBS_DAY=200000`
- Cloudflare 대시보드의 Durable Objects 지출 한도(Spending limits)도 켠다.

## Supabase

| | 무료 | 유료 $25 |
| --- | --- | --- |
| DB 크기 | 500MB | 8GB |
| 데이터 전송 | 월 5GB | 월 250GB |
| 가입자 | 월 5만 명 | 월 10만 명 |
| 서버 | Nano (공용) | Micro (1GB RAM) |
| 그 밖 | 7일 동안 아무도 안 쓰면 멈춤 | 멈추지 않음, 매일 백업 7일치 |

- 호출 수는 문제가 아니다. 400명이 동시에 놀아도 초당 약 13건이다.
- **DB 크기가 먼저 찬다.** 코인 장부(`coin_ledger`)가 코인을 버는 플레이어-시간마다 약 15KB씩 는다. 하루 200 플레이어-시간이면 약 5개월, 하루 1,000이면 약 1개월에 500MB가 찬다. 유료 8GB면 하루 1,000에서 1년 넘게 간다. 오래 가려면 장부를 하루 단위로 묶어 줄이는 작업이 필요하다.
- 데이터 전송은 플레이어-시간당 약 0.3MB로 어림했다(잰 값 아님). 무료 5GB는 하루 약 500 플레이어-시간까지다.
- 지금 DB가 얼마나 찼는지는 이번에 보지 못했다(대시보드 로그인이 풀려 있었다). Supabase 대시보드 → Reports 또는 Database에서 볼 수 있다.

**권장 순서**: 출시 전에는 둘 다 무료. 사람이 들어오기 시작하면 Cloudflare 유료를 먼저(무료 하루 한도가 먼저 막힌다). 하루 500 플레이어-시간을 넘거나 DB가 300MB를 넘으면 Supabase 유료.

## 예전 최적화 점검 결과

Cursor가 해 둔 장치(핑 25초·끊김 판정 75초, 사람 없으면 알람 해제, 움직임 압축, 가까운 사람 우선, 1.15초 보간, 예산 장치의 UTC 날짜)는 맞게 동작했다. 대신 아래 잘못이 있어 고쳤다(커밋 `3b5f6eb`, 테스트 `test/traffic.test.mjs`).

1. **(큰 것) 누가 들어오거나 나갈 때마다 방 안의 모든 탭이 추첨 확인과 지갑·세계 다시 읽기를 했다.** 사람 수의 제곱으로 늘어서, 50명이면 시간당 추첨 호출 약 3.7만, Supabase 호출 약 3.7만, Worker 요청 약 2.4만이었다. 무료 하루 한도를 몇 시간 만에 다 쓰는 양이다. 이제 실제로 접속한 순간에만 한다. 서버도 같은 5분 추첨을 방마다 한 번만 처리한다(옛 탭 대비).
2. **(큰 것) 코인이 쌓이면 방 알람이 5초마다 깼다.** 코인 정산은 30초마다인데 알람은 5초 뒤로 잡혀, 코인을 버는 방 하나가 시간당 약 1,440번 깨고 보고했다. 이제 정산할 때에 맞춰 깬다. 알람 주기 숫자(5초·60초·30초)와 "사람 없으면 알람 해제"는 그대로다.
3. 코인 정산이 실패하면 코인이 생길 때마다 전체를 다시 보냈다(장애 때 줄 쓰기 한도를 몇 분 만에 소진). 이제 30초 뒤 알람에서 다시 한다.
4. 예산 장치가 세지 않던 DO 호출(알람 자체, 추첨, 접속 때 프로필 읽기, 응원이 다른 방 7곳에 보내는 것)을 이제 센다.
5. 80% 단계에서 움직임 메시지를 줄이는 설정이 실제 방식(DO)에는 적용되지 않았다. 이제 적용된다(약 23% 감소).
6. 길이 동서남북으로 나 있어 축에서 1~4도 비껴 걸으면 움직임을 초당 최대 6.5번 보냈다. 이제 약 0.4번이다. 받는 쪽 움직임은 같다.

이 수정 전 무료 용량은 하루 75~150 플레이어-시간이었다.

## 그 뒤 고친 것 (2026-11-22 밤)

아래 "남은 것"의 중간 두 줄과, 같은 점검에서 나온 작은 두 가지다. 테스트 `test/traffic-tabs.test.mjs`.

1. **숨긴 탭.** 5분 넘게 숨은 탭은 연결을 정상 종료(1000)한다. 방은 나간 것으로 보고 자리를 비우며, 아무도 없으면 알람도 걸지 않는다. 다시 보면 같은 길로 붙고 지갑·세계를 한 번, 받은 소식을 한 번 읽는다. 방이 차 있으면 대기 줄이나 다음 방(2~8)으로 간다. 휴대폰을 1분 잠그는 정도로는 끊지 않는다. 숨은 탭에서는 멍때리기 코인을 보내지 않는다(전에는 시간당 30번, 60코인). 효과: 잊힌 탭 하나가 5분 뒤부터 쓰는 것은 0이다. 전에는 방 자리 하나와, 그 방에 사람이 그 탭뿐이면 방이 깨어 있는 시간 시간당 450 GB-s(무료 하루 13,000의 약 3.5%)를 계속 잡았다.
2. **코인 정산 뒤 지갑 다시 읽기.** 정산 알림(`WALLET_SYNC`)에 새 잔액을 싣는다. 화면은 읽지 않고, 10분에 한 번만 확인으로 읽는다. 잔액은 `coin_batch`가 돌려줘야 해서 **SQL 하나(`migrations/2026-11-22-coin-balance.sql`)를 돌린 뒤부터** 줄어든다. 그 전에는 지금과 같다. 효과(돌린 뒤): 코인을 버는 플레이어 한 명이 한 시간에 Worker 요청과 Supabase 읽기를 각각 60~120에서 6 이하로. 위 표의 "움직이며 노는 사람"은 Worker 요청과 Supabase 호출이 각각 약 30~40이 된다. 무료에서 Worker 요청 한도에 닿는 때가 약 800에서 약 2,500 플레이어-시간으로 늦춰진다(먼저 닿는 것은 여전히 줄 쓰기다).
3. **예산 hard의 열린 탭.** hard에서 끊긴 탭이 60초마다 하던 지갑·세계 다시 읽기를 5분마다로 줄였다(보이는 탭 하나가 시간당 120 → 약 28, `/rt/gate` 확인 포함). hard로 닫힌 탭은 한국 시간 오전 9시(UTC 0시) 뒤 1분 안에 흩어져서 다시 들어온다. 전에는 다시 읽어 들일 때까지 꺼져 있었다. 방도 hard일 때 새 연결에 503 대신 'down'을 알려, 다시 붙으려는 탭이 30초마다 방을 깨우지 않는다.
4. **손님 토큰 다시 받기.** 연결이 두 번 실패한 뒤로 재시도마다(0.8~30초) `/rt/guest`를 불렀다. 이제 Worker가 토큰을 거절했다고 알릴 때(4001)와, 그 신호가 없는 예전 Worker를 위해 실패가 이어지는 동안 다섯 번째 뒤 한 번만 부른다. 망이 1분 끊기면 전에는 약 5번(그 뒤 30초마다 한 번), 이제 많아야 1번이다.
